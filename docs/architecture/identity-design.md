# Child-owned identity and verified Python API boundary

FORMA-0038. Recorded 2026-10-26. Owner: Saurya; peer reviewer: Shreesh; lead: Codex. This is a proposed implementation design informed by inspected maintained-library source, not an implemented login system. The shipped neutral blueprint still permits `auth.mode: none` only. Password, TOTP/recovery, social-provider and protected-API acceptance remain open until separately implemented and tested.

## Maintained implementation candidate and evidence

Use the maintained Better Auth Node integration with PostgreSQL and its username/two-factor plugins as the first candidate. The existing application repository pins Better Auth 1.7.12 and pg 8.23.1; these versions were inspected, not installed into this skeleton or automatically approved for its next release. Recheck advisories, runtime compatibility, license notices and maintained-version behavior before adding a pinned dependency/lock here. No bespoke password hash, OTP algorithm, cookie signature, OAuth flow or JWT scheme is proposed.

## Ownership, storage and organization scope

Each generated authenticated app owns its Node auth adapter/configuration, exact maintained dependencies, PostgreSQL identity migrations and application authorization policy. All required Forma adapter source ships physically with the child. Normal declared third-party packages remain installable under their licenses. No seller Kernel session, seller account database, private Forma registry, licensing-signing service or sibling checkout is a runtime dependency.

Identity PostgreSQL owns users, normalized identifiers, credential/provider accounts, verification/challenge state, revocable sessions and the maintained plugin's MFA/recovery tables. Child-owned tables record organization membership/roles, server-derived session assurance and security audit events where not already supplied by the maintained library. Use reviewed foreign keys/unique constraints and additive checksum migrations. Do not edit applied migration source or run schema reset on retained data. Runtime and migration database privileges should be separated before production.

First supported organization model: one customer organization per deployment, many users, with immutable app/organization IDs in trusted server configuration. Username/email uniqueness is global within that child identity store, not a separate namespace per UI-selected organization. A future multi-organization module needs explicit membership queries, server-validated active-organization selection and cross-organization tests; changing a client organization ID must never choose authority. Separate customer deployments receive separate databases, secrets, origins and cookie namespaces.

Existing Kernel PostgreSQL, Care SQLite and other app databases remain untouched by this design. For the neutral generated records example, a later authenticated migration must add server-owned record scope and a reviewed rule for old unowned synthetic rows. Do not silently assign old data to the first signup, expose it to every user or reset it to make authentication tests pass. Unknown/unowned rows deny access until an explicit reviewed adoption/migration handles them.

## Identifier and credential policy

- Adopt explicit ASCII username rules compatible with the maintained plugin (initially 3–30 letters/digits/underscore/dot), lowercase canonical username and a separate optional display label. Keep human display names Unicode-capable. Confirm the selected plugin's configured rules and database unique constraint in implementation.
- Use the maintained email validation/normalization path and document the resulting canonical comparison. Do not invent provider-specific dot/plus rewrites. Verify case-equivalent duplicate and concurrent registration behavior at the database boundary. Changing an email requires a verified flow and reauthentication; a matching unverified address never links accounts automatically.
- Password registration/login/reset are maintained-library operations. Candidate limits are a configurable minimum of 12 and maximum of 128 characters within supported library bounds; do not trim or normalize passwords. Do not expose passwords, hashes, reset tokens or TOTP secrets in logs, source artifacts, analytics, generic config or browser persistence.
- Require configured verification/reset delivery and email verification for the normal password account lifecycle. A missing mail transport is an explicit unsupported/unconfigured state, not a pretend sent email or a hidden bypass. Disposable test fixtures may create synthetic verified identities internally; there is no production test-login route.
- Return generic registration/reset/sign-in responses where enumeration matters, while preserving stable localized error codes and safe operational diagnostics. Use library-backed per-IP/per-account abuse limits, with trusted-proxy configuration explicit; arbitrary forwarded IP headers cannot choose a rate-limit identity.
- Keep automatic provider account linking disabled by default. Later linking requires an already authenticated/recently verified account, verified provider identity and explicit user action under tested policy. Each Google/Facebook/GitHub/Microsoft/Apple adapter and actual provider sign-in/denial remains separately accepted.

## TOTP, recovery and session assurance

The first authenticated candidate is username/email plus password, with authenticator TOTP and recovery through the maintained plugins. TOTP enrollment requires recent authenticated verification, displays its secret/URI only in the intended transient enrollment view and completes only after a valid proof. Use maintained secret encryption and controlled server key storage/rotation; do not copy encryption code into domain templates. Recovery defaults are encrypted in the inspected version, not hashed. Show newly generated codes only in their controlled flow, invalidate replaced codes and test single-use under simultaneous requests.

The inspected password sign-in hook removes its provisional session while MFA is pending and creates an authenticated session after successful challenge consumption. That property must be verified through actual HTTP/PG tests. A client flag, `user.twoFactorEnabled` or a successful first-factor response is never sufficient to authorize the Python API.

Represent the assurance of a particular session using trusted server-side state bound to its maintained session ID. If the library does not provide all needed assurance fields, an app-owned assurance row may record method, verification time and policy generation only from verified maintained-library lifecycle hooks. This is application authorization metadata, not a custom bearer token/signature. Hooks and their order need tests before they may populate it. No value supplied by a browser can create an assurance record. In-flight challenges are not usable application sessions.

Initially require MFA for privileged roles; allow an explicit server policy to require it for all members. Users needing enrollment may reach only the limited account/enrollment workflow until proof, not domain records or admin operations. Enabling mandatory MFA or changing relevant security policy must invalidate/re-evaluate old sessions; enrollment alone cannot upgrade earlier sessions' assurance. Reauthentication gates disable/reset MFA, recovery-code regeneration, identifier changes, linking and privileged actions. The server must reject unsupported trusted-device shortcuts even when a native caller sends the flag; hiding a checkbox is insufficient.

Important unsupported combination: do not enable social-provider plus mandatory-local-MFA merely by turning on two plugins. The inspected hook does not prove that behavior. A later maintained flow must establish a bound pending challenge and verified session assurance for social callback users, or the configuration remains rejected. Likewise provider-side MFA claims are not assumed without validated provider-specific assurance policy. Keep allow-passwordless/skip-verification/trusted-device behavior conservative until explicitly tested.

Use opaque maintained sessions, HttpOnly cookies, production Secure/appropriate SameSite and an app-specific cookie namespace. Production cookies must be host-scoped with restrictive path/domain settings supported by the selected library. Cookies are not isolated by port; different local apps must not share a cookie name or secret merely because they run on localhost. Disable session cookie caching for authorization. Revoke sessions on logout, password reset and security changes as policy requires; read membership/role state authoritatively. Never promote the first browser signup to administrator; bootstrap/invitation is an explicit operator-controlled, audited workflow.

## Selected Node-to-Python candidate: authoritative introspection

Prefer per-request introspection against the same child app's maintained Node auth service for the first supported boundary. This avoids inventing JWT issuance/verification and avoids a stale offline token authorizing a revoked session. A future maintained JWT/JWKS option would need issuer/audience/algorithm/key-rotation/expiry checks and an explicit revocation tradeoff; it is not silently interchangeable with this candidate.

Proposed request sequence:

1. Browser uses the child same-origin auth/controller and business routes. Maintained auth handlers manage cookies/challenges. The business bridge rejects foreign write Origin/CSRF, bounds payloads and ignores user/role/organization/assurance headers. The current public bridge strips cookies; it must not be relabeled authenticated unchanged.
2. The future authenticated bridge sends only the required opaque child session cookie, the validated operation with bounded content headers, and the already-validated Origin on cookie-authenticated writes to its fixed private Python service. No client-chosen upstream URL, arbitrary forwarded headers, seller identity or model credential crosses this boundary. For cookie-authenticated writes, the bridge enforces the configured public origin and Python independently verifies the allowed origin; missing-origin native business agents use a separately authenticated/scoped contract, not an undocumented human-cookie bypass.
3. Python treats that cookie as an unverified credential. Before every protected read/write it asks a fixed, trusted child identity introspection adapter. The adapter wraps maintained `auth.api.getSession` using database-authoritative/disable-refresh checks, then reads current membership/role/session-assurance policy. It never trusts caller-supplied identity claims. A custom HTTP adapter around the maintained validator is not a replacement cookie/token algorithm.
4. The introspection URL is server deployment configuration, never derived from Host, request parameters, redirects or client headers. For the initial single-host development deployment it is fixed loopback/private transport. Cross-host production requires authenticated TLS/service transport and trusted proxy configuration before support; do not expose reusable cookies over plaintext networks or treat loopback alone as user authentication.
5. A minimal successful response contains server-configured app ID, user ID, organization ID, current permission set, session expiry and policy-sufficient assurance. Do not echo the raw session token, provider tokens, email/profile details, backup codes or enrollment secret. Responses are no-store. Python checks shape, expected app/organization, expiry, assurance and action/record permission, then executes the child-owned domain service with server-derived scope. It never authorizes from an `X-User-ID`/role header or supplied owner field.
6. Missing/forged/expired/revoked/challenge-only credentials deny with 401; insufficient organization/role/assurance denies with 403; introspection transport/database failure denies operation with a generic 503. No cached positive authorization or synthetic principal fallback is permitted. The initial public starter remains a deliberately separate mode; selecting protected identity cannot leave its public routes active.

Introspection is not fully specified just by choosing a URL. FORMA-0039 must prove cookie transport/filtering, authoritative queries, failure/timeout/body limits, revocation/role-change behavior and no recursion between proxy/introspection routes. A fixed minimal read adapter should use `disableRefresh` so Python checks do not need to relay session-refresh cookies; normal maintained browser auth routes own refresh. Limit internal response size and timeout, reject redirects and do not log request cookie/header contents. Rate-limit introspection without substituting a stale allowed principal when overloaded.

Revocation guarantee is bounded: an authorization check made after a completed revocation/role-change must deny; a mutation already authorized/in flight cannot be retroactively undone. Define transaction/step-up behavior for especially sensitive operations rather than claiming impossible atomicity across PostgreSQL identity and a separate domain database. Audit actor/scope/result without storing credentials.

## Direct API threat acceptance — FORMA-0039 and follow-ons

| Scenario | Required acceptance evidence |
| --- | --- |
| No session, forged/expired/revoked session, pending MFA | Direct Python read/write denies, no domain mutation; valid sessions use maintained DB validation, not frontend state. |
| Credential replay across child apps/local ports | Separate cookie namespaces/secrets/stores, expected app/organization response checks and fixed introspection target reject cross-app authority. |
| Forged owner/role/organization/MFA headers or JSON | Ignored/rejected; server-derived principal and record-scoped query decide access, including direct requests without navigation. |
| Privilege/member removal and revocation | Requests checked after commit deny immediately with cookie cache disabled; unavailable identity service never fails open. |
| Password reset/verification | Single-use/expiry, anti-enumeration, configured delivery, session revocation and concurrent token reuse are tested with disposable PG fixtures. |
| Username/email duplicates | Normalization and DB unique constraints reject case-equivalent/concurrent registrations; no unverified automatic linking. |
| TOTP setup, recovery and assurance | Enrollment proof, encrypted secrets, concurrent recovery-code single use, challenge binding/expiry, direct shortcut/trusted-device rejection and safe regeneration pass actual adapter tests. |
| Social callback and MFA policy | Password-hook behavior is not assumed to cover providers; unsupported combinations fail before generation until separate real flow/assurance tests pass. |
| CSRF, Origin and return URLs | Foreign/missing cookie-write Origin, forged forwarded headers, redirects and untrusted callback targets deny; native scoped agents remain a distinct route/credential model. |
| Introspection failure or SSRF attempt | Fixed server target, no redirects, bounded response/timeouts; caller cannot choose URL or scope; errors contain no token, SQL or path. |
| Generated package independence | Installed external consumer includes all child identity/authorization/migration source, uses its own disposable PG/domain stores and has no seller Kernel/private-package dependency. |
| Existing data/auth-mode transition | Migration preserves retained data and explicitly handles unowned records; switching a config flag cannot leave public domain routes accessible. |

## Concrete disposable test prerequisites

Codex verified a usable Docker daemon and the cached `postgres:17-bookworm` image, exercised disposable PostgreSQL readiness and removed that test instance. Host PostgreSQL client binaries are not required: an isolated container can supply PostgreSQL and its client. This removes a resource blocker for the next synthetic identity fixture; it is not an authentication test performed by this documentation task.

For FORMA-0039, create a uniquely named temporary container/store, random synthetic credentials kept in a private temporary environment file/process environment, a loopback-only unused port and fixture-specific database names. Run the selected child identity migrations against that target, then remove only those fixture resources after verification. Never reuse the owner's Kernel/PostgreSQL volume, Care SQLite, local Google config or a default DATABASE_URL inherited from an unrelated process. Check the explicit fixture target before migration, prohibit credential dumps and record sanitized results. A controlled local mail outbox may capture synthetic verification/reset messages for automated tests; it is not real delivery acceptance or a production login bypass.

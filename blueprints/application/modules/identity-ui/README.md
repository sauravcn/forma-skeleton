# Optional identity presentation candidate — FORMA-0031

This is **view-only source**, not an authentication module enabled by the generator. The public starter still rejects auth configuration. This directory is not selected by the blueprint manifest: consumers do not receive or enable it automatically. No password verification, delivery, provider connection, session creation, MFA assurance, account recovery policy or authorization occurs here.

A future integration must physically include these sources and import `src/styles.css` from an app-owned layout. `AuthPresentation` accepts a controlled `view` (`login`, `verify`, `resetRequest`, `reset`, `challenge`, `recovery`), `variant` (`minimal`/`split`), required async `onSubmit({view, values})`, optional `onNavigate(nextView)`, and `providers: [{id,label,onSelect}]`. Providers are absent by default; only explicit trusted app callbacks render buttons. Provider labels are ordinary React text. No Google/Facebook integration is implied by rendering a button.

The controller binds current challenge/session/recovery tokens server-side, validates fields, maintains CSRF/origin/state/PKCE requirements through the maintained identity library, and owns view transitions. This view supplies neither identity nor roles nor an MFA-complete flag. A challenge/enrollment screen is never evidence of verified assurance. Social sign-in plus mandatory local MFA is unsupported until separately implemented and tested. Do not pass tokens through DOM fields, logs, browser storage or public props. Credentials exist transiently in native form inputs and callback values; callbacks must not log/persist them. Native form values clear after submission and view changes. Maintain all stronger lifecycle behavior in the server controller.

`busy` disables inputs/actions; requests also disable actions while awaited. Callback failures and external `errorCode` display only generic catalog text, focus a linked alert, and never render exception messages. `noticeCode: 'accepted'` displays “Check your inbox if eligible”; it proves neither mail delivery nor queueing. Username collision privacy and other server policy must not be inferred from these generic view errors. Reset/challenge/recovery submissions do not automatically grant access or navigate.

English strings are local `en.js`; a parent may provide a complete reviewed `messages` catalog. HTML IDs come from React `useId`, not translated identifiers. Stable view/field/provider IDs never depend on labels. Screen-reader/RTL/locale completeness still requires acceptance in the actual app.

## Full app-owned replacement and parent theme

Pass `components: {AuthLayout, AuthField, AuthButton}` to replace complete DOM structures, not only style wrappers. Default `AuthLayout({variant,title,aside,children})` contains all form content; a replacement may use any parent layout but must render children and a labeled accessible region. `AuthField({id,label,errorId,...nativeInputProps})` must preserve an associated label, input id/name/type/required/disabled/autocomplete, `aria-invalid` and error association. `AuthButton` must preserve native type, disabled and click behavior. The heading, form submission, error focus and controller remain owned by `AuthPresentation`. These are trusted local JavaScript components, never JSON/downloaded code.

All CSS selectors begin `.forma-identity`; no body/reset/global element rules are supplied. Parent `--app-*` semantic CSS variables control colors, typography, surfaces, borders, radius, focus and errors. Defaults inherit where possible. Both structures respond to narrow screens; supporting aside content belongs entirely to the app. Replacement layouts may replace all CSS and inherit their own parent design. Token overrides are not a contrast certification.

## Verification and limits

From the authoring repository run `node tests/blueprint-consumers/run-auth-presentation.mjs` after a fresh successful neutral-consumer test. It physically copies optional module source into its own temporary generated Next consumer fixture, performs its own npm ci from the copied generated package/lock with local ordinary dependencies, serves on an isolated loopback port, and removes its fixture afterward. The base generated consumer is not modified. Synthetic callbacks record field **names only**, never values.

The actual browser proof covers minimal/split desktop/mobile screenshots and parent font/color overrides, minimal/split rendering, full layout replacement, opt-in provider callback, each controlled form/challenge/recovery view, cleared password/code inputs, generic focused errors, no localStorage, mobile overflow and page errors. It does not exercise a real identity server, send email, sign in, complete MFA, link providers, prove account ownership or certify full keyboard/screen-reader/RTL/contrast accessibility. Those require integration and separate maintained-library acceptance. There is no seller branding, private source import or new dependency.

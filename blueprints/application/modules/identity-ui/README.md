# Optional identity presentation candidate — FORMA-0031

This is **view-only source**, not an authentication module enabled by the generator. The public starter still rejects auth configuration. This directory is not selected by the blueprint manifest: consumers do not receive or enable it automatically. No password verification, delivery, provider connection, session creation, MFA assurance, account recovery policy or authorization occurs here.

A future integration must physically include these sources and import `src/styles.css` from an app-owned layout. `AuthPresentation` accepts a controlled `view` (`login`, `verify`, `resetRequest`, `reset`, `challenge`, `recovery`), `variant` (`minimal`/`split`), required async `onSubmit({view, values})`, optional `onNavigate(nextView)`, and `providers: [{id,label,onSelect}]`. Providers are absent by default; only explicit trusted app callbacks render buttons. Provider labels are ordinary React text. No Google/Facebook integration is implied by rendering a button.

The controller binds current challenge/session/recovery tokens server-side, validates fields, maintains CSRF/origin/state/PKCE requirements through the maintained identity library, and owns view transitions. This view supplies neither identity nor roles nor an MFA-complete flag. A challenge/enrollment screen is never evidence of verified assurance. Social sign-in plus mandatory local MFA is unsupported until separately implemented and tested. Do not pass tokens through DOM fields, logs, browser storage or public props. Credentials exist transiently in native form inputs and callback values; callbacks must not log/persist them. Secret inputs clear after every submission; a failed same-view callback preserves only the nonsecret identifier/email for retry. All form values clear on view changes. Maintain all stronger lifecycle behavior in the server controller.

`busy` disables inputs/actions; requests also disable actions while awaited. Callback failures and external `errorCode` display only generic catalog text, focus a linked alert, and never render exception messages. `noticeCode: 'accepted'` displays “Check your inbox if eligible”; it proves neither mail delivery nor queueing. Username collision privacy and other server policy must not be inferred from these generic view errors. Reset/challenge/recovery submissions do not automatically grant access or navigate.

English strings are local `en.js`; a parent may provide reviewed `messages` overrides. Overrides reject unknown keys, empty/non-string values and mismatched named placeholders. Provider action text is one complete `{provider}` message, so a locale may reorder the provider name without concatenated fragments. HTML IDs come from React `useId`, not translated identifiers. Stable view/field/provider IDs never depend on labels. Screen-reader/RTL/locale completeness still requires acceptance in the actual app.

## Full app-owned replacement and parent theme

Pass `components: {AuthLayout, AuthField, AuthButton}` to replace complete DOM structures, not only style wrappers. Default `AuthLayout({variant,title,aside,children})` contains all form content; a replacement may use any parent layout but must render children and a labeled accessible region. `AuthField({id,label,errorId,...nativeInputProps})` must preserve an associated label, input id/name/type/required/disabled/autocomplete, `aria-invalid` and error association. `AuthButton` must preserve native type, disabled and click behavior. The heading, form submission, error focus and controller remain owned by `AuthPresentation`. These are trusted local JavaScript components, never JSON/downloaded code.

All CSS selectors begin `.forma-identity`; no body/reset/global element rules are supplied. Parent `--app-*` semantic CSS variables control colors, typography, surfaces, borders, radius, focus and errors. Defaults inherit where possible. Both structures respond to narrow screens; supporting aside content belongs entirely to the app. Replacement layouts may replace all CSS and inherit their own parent design. Token overrides are not a contrast certification.

### Compact default presentation (October 27)

The default minimal panel is approximately 400px wide; the split variant adds a contentful supporting panel and collapses to one column on mobile. Both remain source-owned and replaceable through `components.AuthLayout`. The layout receives the existing `variant`, `title`, `aside`, and `children` props. App themes can replace the complete DOM rather than only colors.

`AuthButton` now receives `variant: primary | social | tertiary` as a presentation hint. Custom button replacements should consume this prop rather than forward it to the DOM. Primary submits, outlined social actions, and lightweight navigation have distinct namespaced styles. Five decorative inline SVG marks use currentColor; they load no third-party assets. Provider callbacks and server-derived configuration remain authoritative; a displayed MOCK mark does not represent a live integration.

All ten existing states retain their callback/field contracts. `asideEyebrow`, `asideTitle`, `asideBody`, and `orContinue` are new whole English messages, subject to the existing validated override contract. Form controls inherit parent semantic typography/tokens. Initial rendering leaves focus in place; subsequent state changes still focus the heading, errors retain their focused alert, and actionable controls have visible keyboard focus. A programmatically focused heading has no decorative outline.

`npm run test:auth-presentation` exercises physically copied optional UI with its own installed dependencies: ten state captures, five provider icons, split desktop/mobile columns, parent font/color inheritance, full layout replacement, controlled callbacks and secret clearing. Its synthetic view-only callbacks do not prove actual login/MFA/provider/network delivery; the separate installed authenticated/mock consumer gates remain required.

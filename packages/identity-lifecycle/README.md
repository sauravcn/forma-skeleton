# Non-shipped password lifecycle candidate

This private package tests Better Auth 1.7.12 and pg 8.23.1 against an isolated PostgreSQL 17 container. It is not part of generated apps. Blueprint authentication remains `none`; this package establishes no MFA assurance, tenant authorization, production email delivery, social login or production readiness.

Run `npm run test:identity-lifecycle` from repository root. Docker must be running with the cached `postgres:17-bookworm` image. Tests allocate a random loopback port, synthetic credentials, tmpfs database and private temporary env file; cleanup removes their container and temporary directory. They never connect existing application databases. No token-bearing URLs, passwords or session cookies are logged or persisted as test artifacts.

`createPasswordIdentity` requires explicit loopback `databaseUrl`, >=32-character `secret`, slug `appId`, exact loopback `publicOrigin`, async `sendMail({kind,to,url,token})`, and async `onDeliveryFailure({kind,code})`. Missing mail callback, redacted operational reporter or database target rejects before constructing the pool. `initialize()` runs maintained migrations before serving; `handler(req,res)` mounts maintained routes at `/api/auth/*`; `close()` closes the owned pool. The transport must reject on delivery failure. Test mail capture is private in-memory only, never evidence of real delivery. No executable production service or automatic account provisioning is supplied.

Maintained endpoints used by the proof:

- POST `/api/auth/sign-up/email`: `{email,username,name,password}`; passwords 12–128 characters, not trimmed. Usernames 3–30 ASCII alphanumeric/underscore, case-normalized; emails follow maintained canonicalization. Signup does not create an authenticated session.
- GET `/api/auth/verify-email` through the maintained emailed URL; verified email required before sign-in.
- POST `/api/auth/sign-in/email` or `/sign-in/username`; successful maintained session cookie is HttpOnly and app-prefixed. Local HTTP proof is not a production HTTPS cookie configuration.
- POST `/api/auth/request-password-reset`: `{email,redirectTo}`. Existing/unknown email requests have matching generic JSON. Username availability is not private: maintained username collision responses differ; do not market universal enumeration resistance.
- POST `/api/auth/reset-password`: `{token,newPassword}`; maintained expiring, single-use token, password hashing and session revocation.
- GET `/api/auth/get-session`: authoritative current session, cookie cache disabled.
- POST `/api/auth/change-password`: `{currentPassword,newPassword,revokeOtherSessions:true}` with session cookie; maintained current-password validation and session replacement. POST `/api/auth/revoke-other-sessions` retains current session and revokes others.

Browser callers must use the configured Origin and maintained credential/CSRF rules. No role, organization, user ID or MFA state supplied by the browser grants authorization. Future frontend adapters must translate maintained error codes through app localization, never render token URLs or raw server traces. Password reset/verification URLs belong only in the recipient channel. No public test-login endpoint exists.

Current executable evidence: actual HTTP signup, pre-verification sign-in denial, email verification, email/username sign-in, lowercase username storage, case-equivalent email duplicate handling, concurrent case-equivalent username uniqueness, maintained hash verification, hostile-Origin denial, generic reset responses, expired and reused reset denial, revoked stored sessions and old-cookie rejection. Reset expiry is induced only in the disposable test DB; verification expiry uses actual elapsed time and maintained token validation. The factory disables library logging to avoid accidental sensitive callback/DB diagnostics; a production redacted operational logging policy remains future work.

Email signup uses an additional bounded two-connection PostgreSQL lock pool and a two-second advisory-lock timeout. All participating service instances serialize the same canonical email before calling the maintained HTTP handler (including its validation and rate limits); successful signup responses normalize to `{status:true,message:"Check your inbox if eligible"}`. This avoids misclassifying arbitrary 422 insert failures as duplicate email. Password/token hashing stays entirely maintained. Username availability remains public. Invalid inputs, username collisions and database/locking failures retain errors. Email transport outages use the request-accepted policy below. The lock is released in `finally`; a failed unlock destroys the connection. Hash collisions only serialize unrelated email requests. Tests assert concurrent equivalent emails produce the same generic 200 payload and one identity. Tests hold the same email lock to verify bounded 503/no insertion, then release it and retry successfully; invalid password and oversized body stay errors. Successful response headers are retained without a stale content length. This assumes all signup writers use this wrapper; direct internal adapter writers are outside the public API contract.

Email request responses deliberately do **not** prove delivery. Valid signup, reset-request and verification-resend responses use the same non-assertive 200 payload, including during mail transport failure. Returning 503 only for existing/eligible addresses would disclose eligibility during outages. Tests explicitly compare existing/unknown reset and resend responses, and duplicate/new signup responses, under a failing transport. Accounts remain unverified and signup never creates a session. Invalid-input/rate-limit failures remain errors; signin failures are never converted to success.

Better Auth signup's background helper catches callback exceptions. The adapter catches transport errors without logging secrets, records a request-scoped failure, and invokes the explicitly required redacted `onDeliveryFailure({kind,code:'MAIL_TRANSPORT_FAILED'})` operational callback. No recipient, token, URL or password is sent to that reporter. Reporter errors also cannot change public eligibility responses. Test capture demonstrates this contract, not real delivery. This prototype has **no durable outbox or automatic retry**; the integrator must provide monitored delivery/retry operations, and a recipient may need resend. We do not assert that "accepted" means queued durably. Mail outage timing may still differ with real provider latency; timing-floor/queue acceptance is future operational work. This contract favors non-disclosing HTTP responses over an actionable per-recipient outage error.

Tests also verify password-change wrong-current-password denial, successful password change replaces/revokes sessions, explicit revoke-other-sessions retains only current session, and unknown-email/wrong-password responses match, resend recovers after failed delivery, and missing/foreign Origin is denied.

Verification uses maintained expiry and idempotence: expired links fail; replay of a successfully used verification link is a harmless success without a session. This is intentionally not described as a single-use email verification token. Password reset tokens are single-use. Test-only verification lifetime is configured to two seconds through validated `verificationExpiresIn` (1–3600, default3600); no custom token creation is introduced.

The Node wrapper requires exact configured Host and mandatory Origin for every non-GET/HEAD request, including unauthenticated reset requests; library defaults alone did not enforce that case.

Open acceptance includes verified-email address change, production transport retry policy, distributed rate limits, production MFA recovery operations/session assurance, production HTTPS and accessibility/UI acceptance. Full identity story completion must not be inferred from this bounded proof.

## Optional maintained TOTP candidate (FORMA-0042)

The default is still password-only. Only a trusted server setting `enableTotp: true` installs the maintained Better Auth two-factor plugin before its migrations; a client cannot enable that capability. The setting must be a boolean. This changes the private candidate's schema, not generated configuration or any existing app. Existing default-mode tests explicitly prove the two-factor API is absent.

In this option, enrollment requires an authoritative verified-email session and the current password. `POST /api/auth/two-factor/enable` accepts `{password,method:'totp'}` (method may be omitted), returns the maintained authenticator URI and recovery codes, and leaves enrollment pending. Only `POST /api/auth/two-factor/verify-totp` with `{code}` finalizes enrollment. The URI and recovery codes are credentials: retain only in the enrolling user's secure channel and do not put them in logs, tickets, screenshots or artifacts.

After enrollment, email/username password sign-in produces a maintained two-factor challenge, not a usable new session. Its challenge cookie must accompany `/two-factor/verify-totp` or `/two-factor/verify-backup-code` with `{code}`. Successful verification consumes that challenge and sets the maintained session cookie. Wrong/past authenticator codes, missing/expired/consumed challenges and reused recovery codes are denied. A real wrong-code HTTP burst proves maintained throttling returns 429 without granting a session or changing enrollment secret/recovery state; no test budget reset occurs inside that burst. GET/PUT factor verification is denied. Separate positive checks reset only the disposable HTTP budget to isolate lifecycle behavior; distributed abuse-resilience operations are not thereby proven. Concurrent use of one recovery code has one winner; the maintained loser can be 401 or 409 depending on whether it observes the consumed value or loses the compare-and-swap race. Do not automatically retry the same recovery code after an ambiguous client network failure; check the resulting session first.

Sensitive endpoints `/two-factor/get-totp-uri`, `/two-factor/generate-backup-codes`, and `/two-factor/disable` require the verified session and `{password}`; rotation replaces prior recovery codes. Password-free enrollment, email/SMS OTP, device trust, `skipVerification`, `skipVerificationOnEnable`, client-supplied `twoFactorEnabled` and recovery `disableSession` shortcuts are unsupported and explicitly rejected server-side. Child trust-device cookies are rejected; hiding a checkbox is not enforcement. The public server-only authenticator generator route remains unavailable. The tests use declared maintained `@better-auth/utils` helpers in memory for URI decoding/current and old code generation, never handwritten cryptography or a public test-login route.

The maintained plugin encrypts TOTP secrets and recovery codes using its configured secret; recovery values are encrypted, **not hashed**. Tests inspect only the disposable store to prove the returned secrets/codes are not stored as plaintext and that maintained verification can use them. This prototype exposes one secret and no key-ring rotation or ciphertext migration workflow. Changing that secret can invalidate cookies/challenges and make existing factor/recovery ciphertext unreadable. No transparent rotation, secure external key storage, backup recovery policy or production enrollment rollout is claimed; loss/compromise requires a separately designed operational procedure. App data and signing secrets are never sent to a seller service.

This is not a session MFA-assurance contract for domain authorization. An enrollment flag is not proof that a particular session completed MFA. Existing pre-enrollment sessions and distinct challenges need explicit lifecycle/assurance policy in FORMA-0039/0043; social-provider callbacks are not supported. The maintained authenticator accepts the current time window and adjacent steps: consumption is per challenge, not a globally single-use TOTP timestep across separate password sign-ins. UI/a11y, org/owner authorization, device/session inventory and generated protected-app integration remain separate acceptance. No `mfaComplete` claim or trusted client header is introduced.
